# 实况照片转换原理

> 这份文档解释：为什么大疆的 3 秒视频要转成实况照片、怎么识别、怎么保证无损，
> 以及我们试过但没采用的方案。

---

## 一、问题背景

大疆 Osmo Pocket 4 拍「实况照片」时，实际生成的是：

```
DJI_20261107111324_0032_D.MP4   ← 约 3 秒的 4K HEVC 视频
DJI_20261107111324_0032_D.LRF   ← 剪辑代理（低码率版本）
```

**没有 JPG。** 相机内部把这一帧"照片"和 3 秒"动态"合成了一个视频。

结果就是：备份到 NAS 后，相册按扩展名判断，这些素材全被当成"视频"，
不会出现在照片时间线里，也不能长按播放。

---

## 二、实况照片的两种标准格式

### 1. 苹果 Live Photo —— **两个文件配对**

```
IMG_1234.JPG    ← 静态图
IMG_1234.MOV    ← 3 秒视频
```

靠一个 UUID 关联：

| 文件 | UUID 写在哪 |
|---|---|
| JPG | EXIF → **Apple MakerNote** → tag `17` = `ContentIdentifier` |
| MOV | QuickTime 元数据 → `com.apple.quicktime.content.identifier` |

两边 UUID 相同 → iOS 相册识别为实况照片（带 LIVE 标记，长按会动）。

> 所以苹果的实况照片**不是单个文件**，是一对。少一个就退化成"图 + 视频"。

### 2. 安卓 Motion Photo —— **单个文件**

```
一个 .JPG 文件：
┌─────────────────────────┬──────────────────────────┐
│  封面 JPEG               │  内嵌 MP4（原样拼接）      │
└─────────────────────────┴──────────────────────────┘
                          ↑
              头部 XMP 写 GCamera:MicroVideoOffset
              （记录 MP4 从文件末尾算起占多少字节）
```

关键 XMP 字段：

```xml
<GCamera:MicroVideo>1</GCamera:MicroVideo>
<GCamera:MicroVideoVersion>1</GCamera:MicroVideoVersion>
<GCamera:MicroVideoOffset>27879745</GCamera:MicroVideoOffset>
<GCamera:MicroVideoPresentationTimestampUs>300000</GCamera:MicroVideoPresentationTimestampUs>
```

## 三、为什么选单文件格式

实测结论：**绿联 NAS 相册认单文件 Motion Photo，不认苹果的 JPG+MOV 配对。**

我们做过对照实验：

| 方案 | 格式 | 绿联相册识别 |
|---|---|---|
| A. JPG + HEVC MOV 配对 | 双文件 | ❌ 不认 |
| B. 单文件 Motion Photo | 单文件 | ✅ **能认** |

### 苹果格式为什么失败

先排除最可能的原因 —— **ContentIdentifier 配对**：

```bash
# 我们的 JPG
[Apple] ContentIdentifier : 43DE0258-0165-4976-AFD0-B2E2FDF640DC

# 我们的 MOV
[Keys] ContentIdentifier  : 43DE0258-0165-4976-AFD0-B2E2FDF640DC
```

**两边完全一致，但不是这个原因。**

真正的差异：

| 项目 | iPhone 原生 | 我们做的 |
|---|---|---|
| 静态图 | **HEIC** | JPG |
| MOV 里的 `still-image-time` 轨道 | **有** | 无 |

- `still-image-time` 不是元数据标签，而是 **MP4 里的一条独立轨道**（handler=meta）。
  `exiftool` 只能改容器元数据，**不能新增轨道**。
- HEIC 这条路也走不通：`exiftool` 无法给 HEIC 写 Apple MakerNote（和 JPG 一样的问题），
  要绕过只能自己写 HEIC 编码器。

所以最终放弃苹果格式，改用单文件 Motion Photo —— 而且它本来就更适合 NAS 场景：

- 一个文件，不怕拆散
- 移动/同步/备份都不会坏
- 安卓手机也能直接看

## 四、怎么识别哪些 3 秒视频是实况

### 双条件判据

```
① 时长在 2.5 – 4.0 秒
② 且没有 DjiCameraLensType 标记
→ 两条都满足才算实况素材
```

### 实测数据（73 个 MP4）

| 类别 | 数量 | 有 `DjiCameraLensType` |
|---|---|---|
| 短片段 2.5–4.0s | **63** | **0 个** |
| 超短 <2.5s（0.30 / 0.88 / 1.58s）| 3 | **3 个** |
| 长视频 >4.0s（11–137s）| **7** | **7 个** |

**63 vs 10，零误判。**

### 控制实验：排除"按日期/固件区分"

| 日期 | 实况 | 非实况 |
|---|---|---|
| 2026-11-01 | 3 | 1 ← 混合 |
| 2026-11-04 | 2 | 2 ← 混合 |
| 2026-11-06 | 8 | 2 ← 混合 |
| 2026-11-07 | 50 | 3 ← 混合 |

5 天里 4 天同一天既有实况又有非实况 → 标记跟的是**内容类型**，不是固件版本或拍摄日期。

**推测原因**：实况照片走"快速抓拍"管线，不写完整镜头元数据。

### 为什么不用别的判据

| 判据 | 为什么不行 |
|---|---|
| 文件大小 | 画面复杂度影响太大（14.5–26 MB）|
| 有无音轨 | 长短视频都有音轨 |
| 分辨率 | 全是 4K |
| 轨道结构 | 完全相同（video + audio + djmd + dbgi + tmcd + mjpeg）|
| 文件名序号 | 和普通视频共用同一个计数器 |

### 为什么双条件比纯时长安全

| 情况 | 纯时长 | 双条件 |
|---|---|---|
| 0.3 秒误抓片段 | ⚠️ 靠边界挡 | ✅ 有标记，排除 |
| 将来出现 3 秒真视频 | ⚠️ **会误转** | ✅ 有标记，排除 |
| 实况照片 | ✅ | ✅ |

**失败方向是安全的**：万一真实况带了标记 → **漏转**（可用 force 清单补救），
而不是把真视频误转成图片（不可逆的体验损失）。

## 五、无损转换的实现

### 结构

```
最终文件 = 封面 JPEG（重新编码） + 原始 MP4（逐字节原样）
                                   ↑
                    XMP MicroVideoOffset 记录 MP4 字节数
```

### 步骤

```bash
# ① 提取关键帧（4K q=1）
ffmpeg -ss 0.3 -i input.mp4 -frames:v 1 \
       -vf "scale=3840:2160:flags=lanczos" -q:v 1 cover.jpg

# ② 原样拼接（视频零改动）
cat cover.jpg input.mp4 > output.JPG

# ③ 写 XMP
exiftool -XMP-GCamera:MicroVideo=1 \
         -XMP-GCamera:MicroVideoVersion=1 \
         -XMP-GCamera:MicroVideoOffset=<mp4字节数> \
         -XMP-GCamera:MicroVideoPresentationTimestampUs=300000 \
         output.JPG
```

### 三重校验

移动原片之前必须全部通过：

1. **大小关系**：文件总大小 = 封面大小 + XMP 里的 offset
2. **偏移正确**：offset 等于原片字节数
3. **MD5 比对**：从文件尾部切出 offset 字节，与原片 MD5 完全一致

```bash
# 第 3 步的实现
tail -c "$OFFSET" output.JPG > extracted.mp4
[ "$(md5sum input.mp4 | cut -d' ' -f1)" = "$(md5sum extracted.mp4 | cut -d' ' -f1)" ]
```

### 无损验证结果

```
原片 MD5: a0cda2dacccb89128d35351d1d283422
提取 MD5: a0cda2dacccb89128d35351d1d283422   ✅ 完全一致
```

提取出来的视频参数也完全不变：`hevc / Main 10 / 3840×2160 / 3.036s`。

### 唯一"有损"的部分

封面那一帧必须重新编码成 JPEG —— 因为你要从视频里抽一帧变成图片，格式必然变，
这是原理决定的，不是实现问题。

用了 **4K + JPEG q=1（最高质量）**，实际肉眼看不出差别。
封面大约 0.3–2.4 MB，取决于画面复杂度。

## 六、体积对比

| 项目 | 单条大小 |
|---|---|
| 原始 MP4 | 平均 20.3 MB |
| LRF 代理 | 平均 2.9 MB |
| **无损实况照片** | **21.0 MB**（原 MP4 + 约 0.7MB 封面）|

转换后原片移入归档区，成品区里：
- 实况照片 = 21 MB（内含完整无损视频）
- 长视频 = 原样保留

**净变化**：省掉了 LRF（每条约 2.9 MB），所以整体还略微节省空间。

## 七、参考命令：从实况照片提取原片

```bash
# 方法一：用内置工具
sudo dji-extract-video /mnt/pocket4/2026-11-07/DJI_xxx.JPG ./output.mp4

# 方法二：手动
SIZE=$(stat -c %s DJI_xxx.JPG)
OFF=$(exiftool -s3 -MicroVideoOffset DJI_xxx.JPG)
tail -c "$OFF" DJI_xxx.JPG > output.mp4
```

提取结果是逐字节无损的原始 MP4。

## 八、清单格式演进

去重清单从 v1 升级到 v2，为了支持"原片移走"这个场景：

```
v1（3 列）: 文件名 | 大小 | 导入时间
v2（4 列）: 文件名 | 大小 | 导入时间 | 状态

状态:
  imported  = 原片在成品区
  converted = 原片已归档到 pocket4_raw
```

**为什么需要状态**：原片被移到归档区后，"目标文件是否存在"这个判断会失效，
导致下次插入相机时重新拷贝。有了状态字段，就能按状态去正确的位置检查。
